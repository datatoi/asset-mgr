# Application audit — 1 October 2026

> Historical findings from the initial audit. Remediation and current semantics
> are documented in [audit-fixes.md](audit-fixes.md). Shared products/items across
> kits and competing pending requests are intentional; they do not require exclusive
> kit membership or reservation.

The implementation had critical tenant isolation and transfer authorization defects. The web and functions builds pass, but successful builds do not establish that the checkout workflow or access controls are correct.

## Scope and evidence

Reviewed Firestore and Storage rules, all six callable functions, web authentication and pages, deployment configuration, and the mobile draft against `CLAUDE.md` (the canonical reference).

Validation used isolated Authentication and Firestore emulators with project ID `demo-asset-audit`, two subscriptions, and synthetic users/items. Client access checks used the real Firebase client SDK and the repository's Firestore rules. Backend checks invoked the compiled callable handlers through `.run()` with synthetic authenticated requests and the real Admin SDK connected to the emulator. This exercises handler logic; it does not test deployed HTTP authentication or IAM. No production data was accessed or changed.

Both projects passed `npm run build` and `npm run lint`. Web lint reported four warnings and functions lint two. The web bundle is about 1.77 MB before compression, 548 KB gzip. Production deployment, browser end-to-end flows, Storage rules execution, and physical NFC hardware were not tested.

## Findings, ordered by priority

### A01 — Critical: forged transfer offers authorize arbitrary holder changes

**References:** `firestore.rules:99`; `functions/src/index.ts:255`.

Any authenticated user may create a transfer document with arbitrary fields. `transferItem` treats a pending document naming the caller as `targetUserId` as authorization, without checking that its creator was the item's holder/owner or that the caller belongs to the item's subscription. `newHolderId` is also supplied independently by the caller.

**Reproduced:** a regular user in subscription A created an offer against an item held by a member of subscription B, named themselves as recipient, and successfully transferred that item to themselves. Knowing the item ID is sufficient; normal read restrictions still apply, but do not prevent this write attack.

**Fix:** validate transfer creation against the authoritative item and caller, preferably in a callable function. Validate subscription, item, initiator, holder, recipient, status, and allowed fields. Acceptance must derive the destination from that validated transfer rather than trust an independent `newHolderId`.

### A02 — Critical: admin authority extends across groups and tenants

**References:** `firestore.rules:61`, `:66`, `:74`, `:94`, `:107`; `functions/src/index.ts:245`; `storage.rules:27`, `:32`.

Catalog writes check `isAnyAdmin()` without checking the document's subscription or group. Any user can register their own subscription and become its superadmin, gaining this authority. `transferItem` likewise treats an admin role in any group as sufficient for any item. Storage catalog paths use the same global admin check, with no tenant/group information in the object path.

**Reproduced:** an admin in subscription A modified a category and deleted an item in subscription B using the client SDK, then transferred another foreign item through the callable handler. Storage exposure was established by source review only. Item creation also permits arbitrary initial holders; delete/recreate can bypass the update restriction on `holderId`.

**Fix:** require matching subscription and an admin role for the document's actual group on every write and direct transfer. Keep tenant/group fields immutable except through explicitly validated moves. Scope Storage paths to tenant/group/catalog IDs and check the corresponding resource. Restrict initial item holders to the intended storage sentinel.

### A03 — High: regular users cannot load their transfer inbox

**References:** `web/src/pages/TransferInbox.tsx:38`, `:45`; `firestore.rules:98`.

The holder and recipient queries omit `subscriptionId`, while read rules require a matching subscription. Both listeners are denied, and neither has an error callback. The result can appear as an empty inbox even when requests exist.

**Reproduced:** both exact query shapes returned `permission-denied` for a regular user. Firestore evaluates potential query results, so client query constraints must satisfy the read rule. See [Firebase query authorization documentation](https://firebase.google.com/docs/firestore/security/rules-query).

**Fix:** add the user's subscription constraint to both queries and handle listener errors visibly. The page also never queries requests initiated by the user or completed/declined requests, so the documented outgoing status view is missing.

### A04 — High: kit requests do not check caller tenancy

**Reference:** `functions/src/index.ts:326`.

`requestKit` verifies that a user document and kit exist, but never compares their subscriptions or checks the caller's group membership. Referenced products and categories are not validated against the kit's tenant/group either.

**Reproduced:** a regular user in subscription A successfully requested a kit in subscription B, creating pending transfers in B.

**Fix:** validate caller membership and all catalog references before selecting inventory or creating requests. Keep the documented subscription-wide read policy separate from group-specific write authority.

### A05 — High: stale or mismatched transfers can overwrite current state

**References:** `functions/src/index.ts:224`, `:249`, `:275`, `:293`.

Items are read outside a transaction and later updated in a batch. A push offer is not checked against the item's current holder. When a caller is already a holder/admin, the supplied transfer ID is never checked for item identity or pending status before it is marked transferred. Destination users and transfer types are not validated.

**Reproduced:** accepting an old offer moved an item away from a later holder. A current holder also marked an unrelated, already declined transfer as transferred while acting on a different item. An admin transferred an item to a nonexistent user with an arbitrary history type.

**Fix:** transactionally read and validate item, transfer, destination, and permissions; reject stale/replayed requests and mismatched references. Derive the holder and audit type from the operation. Direct holder handovers should follow the intended recipient acceptance flow. Firebase documents how [transactions retry when their reads change](https://firebase.google.com/docs/firestore/manage-data/transactions).

### A06 — High: kit selection creates conflicting allocations

**References:** `functions/src/index.ts:362`, `:370`, `:378`.

Available items are selected from `holderId == 'storage'`, but creating a request neither reserves the item nor excludes existing pending requests. Each call selects the first matching item again. This happens even with sequential requests, without concurrency.

**Reproduced:** two callers requested the same kit and both received pending transfers for the same physical item. With A05, approving the second request can take the item from the first recipient.

**Clarification and resolution:** shared kit requirements and competing pending requests are intentional. No reservation or exclusive kit membership is needed. The first valid approval receives the item and closes competing requests; transaction checks prevent later approvals from overwriting that holder (A05).

### A07 — High: onboarding races break the single-subscription invariant

**References:** `functions/src/index.ts:38`, `:51`, `:102`, `:132`.

Registration and joining check membership before their writes, without a transaction or precondition. Concurrent calls can both pass. Merged `groups` maps can retain roles from multiple subscriptions while the final `subscriptionId` names only one.

**Reproduced:** two concurrent registrations for one UID created two subscriptions and left two groups in that user's role map.

**Fix:** transactionally check and establish membership with subscription/group creation. Apply the same invariant to joining and handle repeat calls consistently.

### A08 — High: role assignment accepts foreign members and invalid roles

**Reference:** `functions/src/index.ts:411`.

The caller's role in the supplied group is checked, but the group document, target user's subscription, and allowed role values are not. This can introduce foreign group roles into another subscription's user map and amplify A02.

**Reproduced:** a subscription A superadmin assigned their group's superadmin role to a user whose subscription remained B. Acceptance of arbitrary truthy role values follows directly from the handler code.

**Fix:** validate group existence, caller/target/group tenancy, and the role enum before updating membership.

### A09 — Moderate: the final superadmin and subscription owner can be locked out

**References:** `functions/src/index.ts:179`, `:418`, `:433`; `web/src/pages/MembersPage.tsx:65`.

Role removal allows demoting oneself or the last superadmin. Administrative callables never use `subscriptions.ownerUserId` as an authority override, despite the owner being the highest authority in the canonical model.

**Reproduced:** the sole superadmin, also the subscription owner, removed their own role and could neither restore it through `assignRole` nor create a replacement group. Recovery requires Console/Admin SDK access.

**Fix:** define and enforce owner authority and a last-superadmin invariant transactionally, or block self-demotion where it would leave no administrator.

### A10 — Moderate: unisex garments cannot fulfill ordinary kit requests

**Reference:** `functions/src/index.ts:367`.

The item query requires exact equality with the requester's `male`/`female` gender. Catalog forms support `unisex`, but Profile intentionally does not offer `unisex` for people.

**Reproduced:** an available unisex item with the correct product and size produced `No available item` for a male requester.

**Fix:** accept both the requester's gender and `unisex`, with an explicit selection preference. Validate kit gender consistently too; it is currently ignored.

### A11 — Moderate: comments permit cross-tenant posting and impersonation

**Reference:** `firestore.rules:82`.

Comment creation checks authentication only. It neither checks access to the parent item nor binds `userId` to the caller. Author names, avatars, text, and timestamps are all unvalidated.

**Reproduced:** a regular user in subscription A posted a comment on B's item using B's user ID and a fabricated author name, without a timestamp.

**Fix:** validate parent tenancy, authenticated author, required fields, text type/length, and timestamp. Resolve display identity from trusted profile data when appropriate.

### A12 — Moderate: group tenant reassignment is unrestricted

**Reference:** `firestore.rules:56`.

Superadmin authority is checked by group ID, but writes may change `subscriptionId`. Membership maps and catalog documents are not migrated with that change.

**Reproduced:** a group's superadmin changed its subscription from A to B directly through the client SDK.

**Fix:** make group tenancy immutable. Validate edits against both the original document and proposed data; creation should remain server-controlled.

### A13 — Moderate: auth listeners survive sign-out and account changes

**Reference:** `web/src/auth/AuthContext.tsx:29`.

The cleanup returned inside the `onAuthStateChanged` callback is discarded. The outer effect only unsubscribes from Auth, leaving the user document listener active. `loading` is not reset before fetching a new user's profile, and listener errors do not clear stale profile data.

**Evidence:** source review. Permission revocation may stop an old listener, but its error path still does not clear the stale profile. This is a session state and routing problem; backend authorization uses `auth.uid` independently.

**Fix:** explicitly tear down the previous profile listener on every auth transition and unmount, clear profile state, reset loading, and handle read failures.

### A14 — Minor: schema and resource limits are missing

**References:** `firestore.rules:34`, `:59`, `:99`; `storage.rules:20`; callable argument checks throughout `functions/src/index.ts`.

Profile writes block role/tenant changes but allow other arbitrary fields and types. Catalog and request schemas lack field allowlists, reference validation, and useful string/array bounds. Uploads have no server-side content type or size limits. Malformed data can crash renderers, and unrestricted request/comment/upload creation increases storage and processing costs.

**Fix:** add focused validation and limits at the rules/callable boundary. Preserve the existing good restriction against directly changing `users.groups` or `users.subscriptionId`; a direct role update was correctly denied in the emulator.

## Dependency audit

`npm audit --json` reported 9 affected package entries for web (8 high, 1 moderate) and 15 for functions (4 high, 11 moderate). These totals include development dependencies and multiple entries propagating the same advisory; they are not counts of distinct exploitable app defects.

Reachability needs review before assigning app severity. For example, the [React Router advisory](https://github.com/advisories/GHSA-qwww-vcr4-c8h2) concerns RSC server actions, while this application is a client SPA. The [gRPC certificate advisory](https://github.com/advisories/GHSA-m9gg-hp2v-232j) concerns specific certificate-authentication configurations, not every Firebase use. No direct exploit of these dependencies was established here. Update compatible packages and verify the resulting lockfiles; review major-version recommendations rather than applying `npm audit fix --force` blindly.

## Avatar change completed during the audit

The user confirmed that saving the profile makes the uploaded avatar persist. Previously, an upload only changed a draft form value until Save Changes was pressed. Profile avatars now persist immediately after upload, the uploader awaits persistence before reporting success, and profile snapshots do not overwrite other unsaved form edits. Changes are in `web/src/pages/ProfilePage.tsx` and `web/src/components/ImageUpload.tsx` and preserve the existing UID-scoped avatar path change. Web build and lint passed after these changes. The new browser upload/reentry flow was not exercised during this audit.

## Recommended repair order

1. Close A01/A02 with tenant/group checks and validated transfer creation/acceptance.
2. Repair the ordinary transfer inbox and add transaction checks to approval, onboarding, and role management.
3. Preserve shared kit requirements and competing requests, enforce first-valid-approval semantics, and handle unisex inventory.
4. Add targeted schema limits, fix session cleanup, and finish missing web flows.
5. Review dependency advisories and then complete the separately planned mobile work.
